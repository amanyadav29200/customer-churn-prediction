# Customer Churn Prediction System

A learning-focused, end-to-end machine-learning project that estimates which customers in a fictional telecom dataset are associated with churn. It includes exploratory analysis, leakage-safe preprocessing, five model families, cross-validation and tuning, an explainability report, and an interactive Streamlit app.

## Scope and honest interpretation

The project uses IBM's public Telco Customer Churn sample. IBM describes the company as fictional and the `Churn` field as whether a customer left within the previous month. The data includes account, demographic, and subscribed-service fields. It is a static labeled snapshot: this project classifies **churn risk/status**, but cannot predict an exact future cancellation date. Service columns show subscribed services, not usage volumes. To answer which product a person uses most in usage terms, collect dated product events or measures such as call minutes, data GB, or streaming hours.

Dataset source: [IBM's archived sample repository](https://github.com/IBM/telco-customer-churn-on-icp4d/tree/master/data) and [IBM's dataset description](https://www.ibm.com/docs/en/cognos-analytics/12.0.x?topic=samples-telco-customer-churn). The original CSV and its hash/source notes are in `data/raw/README.md`.

The scores produced here describe a held-out split from this public sample. They are not a promise of business performance or a production-ready retention policy.

## Goals

- Clean and inspect a real telecom churn dataset.
- Compare interpretable and tree/margin-based classifiers.
- Focus evaluation on churn recall as well as precision, F1, ROC-AUC, and PR-AUC.
- Keep imputation, scaling, and encoding inside Scikit-learn pipelines to prevent test-fold leakage.
- Explain global feature reliance with permutation importance and provide a transparent one-feature-at-a-time local sensitivity view.
- Score individual customers or a CSV through a Streamlit dashboard.

## Methodology

### Data cleaning and feature preparation

The loader removes duplicate rows and duplicate customer IDs, converts blank `TotalCharges` values to missing numeric values, maps `Churn` to 0/1, and excludes `customerID` from predictors. The pipeline imputes numeric fields with the median and categorical fields with the most frequent value. Numeric columns are standardized, and categorical fields are one-hot encoded. All of those steps are fitted inside the cross-validation/training pipeline, not on the full dataset.

The EDA notebook reports missingness, duplicates, churn distribution, churn rate by contract/payment method, tenure and charge distributions, a numeric correlation heatmap, and IQR outlier flags. Outliers are flagged for review rather than removed automatically because high charges can be legitimate.

### Model families and the idea behind them

The project compares:

1. **Logistic Regression** — estimates `P(churn | x) = 1 / (1 + exp(-(w·x + b)))`. It learns coefficients by minimizing log loss, with class weights for the minority churn class. It's a strong, explainable baseline.
2. **Decision Tree** — recursively splits features to create groups. A common split measure is Gini impurity, `1 - Σ pₖ²`. Trees are easy to explain but can overfit; depth and leaf size are constrained and tuned.
3. **Random Forest** — averages many trees trained on bootstrapped samples and random feature subsets. Averaging usually reduces the variance of a single tree. It uses balanced class weights.
4. **Support Vector Machine (RBF)** — chooses a separating boundary with a large margin; the radial-basis kernel allows curved boundaries. It uses class weights and probability estimates, but is less directly interpretable.
5. **Gradient Boosting** — adds shallow trees sequentially to correct previous errors. Balanced sample weights are supplied during fitting. It can capture nonlinear patterns but needs tuning to avoid overfitting.

Each model is assessed with five-fold stratified CV on the training split. The CV-F1 leader (ROC-AUC breaks ties) is tuned with a small randomized search. A decision threshold is chosen from out-of-fold training probabilities by maximizing F2 (`β = 2` gives recall more weight than precision). The test split remains untouched until final evaluation.

### Metrics

- **Accuracy** = correct predictions / all predictions. It can hide missed churners when classes are imbalanced.
- **Precision** = TP / (TP + FP): among customers flagged, the fraction who churned.
- **Recall** = TP / (TP + FN): among actual churners, the fraction detected.
- **F1** = harmonic mean of precision and recall.
- **F2** = harmonic mean that weights recall more heavily; used only to choose a training threshold.
- **ROC-AUC** = probability ranking quality across thresholds.
- **Average precision / PR curve** = precision-recall performance, useful when the positive class is less common.

The threshold is a business choice. Lowering it usually catches more churners but also flags more customers who would stay; an operations team should consider outreach capacity and costs before acting.

### Explainability

Global permutation importance shuffles one raw feature at a time in the held-out test data and measures the mean decrease in ROC-AUC. The customer prediction page also replaces one input feature at a time with its training median/mode and displays the change in model score. This is a local sensitivity estimate, **not** a causal explanation. Correlated features can share or distort importance.

## Dashboard pages

1. **Business Overview** — sample size, observed churn/retention, and churn rates by contract.
2. **Customer Prediction** — enter account and service fields, see estimated churn probability, risk band, threshold decision, and approximate feature sensitivities.
3. **Model Performance** — compare CV metrics and inspect held-out confusion matrix and curves.
4. **Customer Insights** — review permutation importance and high-churn segments with at least 30 customers.
5. **Batch Prediction** — upload a CSV, score each row, and download the results.

For batch scoring, include the model's raw feature columns (as shown in the interactive form). `customerID` and `Churn` are not required. Extra CSV columns are preserved in the downloaded output but ignored by the model.

## Common issues

- **`ModuleNotFoundError`**: activate `.venv` and run `python -m pip install -r requirements.txt`.
- **App says model is missing**: run `python train.py` from the project root first.
- **Dataset not found**: restore `data/raw/Telco-Customer-Churn.csv` using the official link in `data/raw/README.md`.
- **CSV batch upload reports missing columns**: match the app's field names exactly; categorical values outside training values are safely ignored by one-hot encoding, but should still be checked for spelling/consistency.
- **Recall is high but precision is low**: raise the sidebar threshold or rework retention capacity/costs; do not judge by accuracy alone.

## Limitations and future improvements

- The benchmark is fictional, static, and not representative of a current company's customers.
- It is a retrospective label. A real churn forecast needs a prediction date, customer histories, and a future outcome window (for example, cancellation in the next 30 days). To estimate time until churn, use dated events and survival analysis.
- Subscription flags are not usage counts. Add monthly call/data/product usage for product consumption analysis.
- Use temporal validation on newer periods, calibration checks, segment-level error analysis, and controlled retention experiments before production use.
- Thresholds and retention suggestions should reflect intervention costs, fairness review, and business capacity.
- SHAP explanations, model monitoring, API deployment, and a proper model registry are potential extensions.

Then read `src/churn/data.py` for cleaning, `src/churn/modeling.py` for pipelines/CV/tuning, `src/churn/explain.py` for model sensitivity, and `app.py` for the dashboard. Change one experiment at a time (for example, CV-F1 selection versus ROC-AUC selection) and record its effect on recall, precision, and the confusion matrix.
